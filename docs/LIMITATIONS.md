# Known limitations, operational and privacy guardrails

**This is a completed, tested *research MVP*, NOT a fully validated production insurance fraud platform.** It is suitable for local demonstration with synthetic data. Do not place real personal/medical records into a public server without substantial hardening, legal review and a data-protection impact assessment.

1. **Dataset and validity:** Included CSVs are synthetic, generated through a documented artificial label function. Performance is only on held-out artificial samples and provides zero assurance of real claims accuracy. No real-world fraud labels or insured populations are bundled.
2. **No underwriting model:** Fraud and underwriting are different prediction tasks. Underwriting output is always unavailable until an independent, tested expected-loss/severity model is implemented and approved.
3. **No manipulation or diagnosis claims:** Image quality, OCR errors, perceptual hashes and identical photos do not establish forgery. The image classifier is an opt-in evidence-type classifier; it is not a validated tampering detector. No medical diagnosis or life risk assessment occurs.
4. **Limited text extraction:** Regex supports common English-language layouts and ISO dates; complex tables, scanned handwriting, multilingual claims, OCR confidence calibration, signature authenticity and region highlights are not supported. Scanned PDFs require the system Tesseract binary.
5. **Synchronous processing:** Training and OCR run synchronously; long jobs should be moved to an isolated job queue with timeouts, worker sandboxing, backpressure and polling before broader use.
6. **Tabular feature contract:** Models require seven common numeric fields derived from user-confirmed values. Features absent at inference are imputed using training statistics and do not automatically lead to fraud suspicion. Cases far beyond training ranges abstain; OOD detection here is rudimentary.
7. **Explainability:** Deterministic rule evidence is transparent, but there are no statistically validated local SHAP explanations, calibrated fraud probabilities, externally validated thresholds, or fairness dashboards. Provisional 80/20 score composition and bands must be validated before deployment.
8. **Privacy and document security:** Uploads are stored with random file names and authorization-checked access. Parsing potentially malicious PDFs/DOCX files still uses third-party parsers in the API process; production needs malware scanning, sandboxed OCR, strict operation timeouts, document sanitization, encryption at rest, key rotation, retention/deletion workflows and sensitive-data minimization.
9. **Authentication/session:** Passwords are salted/hashed; JWT access expires. Production requires refresh-token revocation, HTTPS, hardened cookies or short-lived tokens, CSP, distributed rate limits, login anomaly detection, user management and MFA. Current token is in `sessionStorage`; CSP and XSS review are important. **Do not make this demo internet-facing.**
10. **Business rules:** Shared basic coverage-date and invoice discrepancy rules are advisory, not policy-wording or jurisdiction-specific eligibility checks. The registry supports typed category fields, and simple Health/Travel/Motor consistency checks, but does not implement bespoke legal adjudication for all 14 insurance products.
11. **Audits and reproducibility:** Sensitive events are recorded, but audit logs are not tamper-evident or externally retained. The default Alembic migration is a bootstrap metadata migration, not a production migration history. Model artifacts use Python pickle/joblib and must only be loaded from trusted application-generated paths.
12. **Database scale:** SQLite is for local demonstrations. PostgreSQL, backup/restore, isolation testing, connection pooling and tested Alembic revisions are required for deployment.
13. **Testing boundary:** Automated API, scoring, PDF, data and model-workflow tests ran in the available environment. Not covered here: full browser automation (the test environment blocked Chromium-to-localhost access), GPU transfer-learning performance, penetration testing, malicious PDF fuzzing, large concurrent submissions or real-world calibration.
14. **Reliability:** Use real labeling governance, out-of-sample temporal testing, group splits by insured party, threshold selection with business costs, drift checks, segment audits, human appeals and rollback approvals before affecting real people.

**The product's only safe default recommendation is verification or human-led workflow continuation.** An unverified output cannot accuse a claimant, deny a claim or set binding underwriting premiums.
